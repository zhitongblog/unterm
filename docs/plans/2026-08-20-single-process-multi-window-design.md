# 单进程多窗口设计：退出语义先行

状态：**已实施**（2026-08-23，0.68.2 / 0.68.3）。D1–D5 全部按本文拍板，
W-1 到 W-5 全部落地并在真机验收；第 6 节那个缺陷已单独修掉。逐条落地情况
见第 8 节。

这份文档写作时的结论是「值不值得做」取决于第 2 节能否谈拢，所以第 2 节
写在最前面的位置，实现切片放在后面。原文保留，不改写成事后视角——它记录
的是当时凭什么这么决定。

背景：0.68.1 的启动实测显示 Unterm 开一扇窗要 587ms（热）/ 682ms（冷），
Windows Terminal 是 172ms。差距的成因不是渲染也不是配置加载，是
**每一扇窗都是一个进程，于是每一扇窗都重付一次 GPU 初始化**。

## 0. 收益有多大（实测，不是估算）

`unterm-render` 里的探针，同一进程内连续三轮：

```
round 1: Instance::new 15.3 ms   request_adapter 327.3 ms
round 2: Instance::new 11.2 ms   request_adapter 197.2 ms
round 3: Instance::new 14.8 ms   request_adapter 201.6 ms
```

`request_adapter` **每次调用**都要约 200ms，不是首次特有——所以它不是
「进程冷启动税」，而是「每次枚举适配器税」。反过来说：**复用同一个
adapter 就完全不用付**。

启动 trace（release 冷启动）里每扇窗自己那部分只有：

| 步骤 | 耗时 |
|---|---:|
| `create_surface` | ~0 ms |
| `surface.configured` | 3 ms |

也就是说，单进程多窗口下第二扇窗的图形开销从
**~293ms（adapter 200 + device 37 + instance 15 + 余量）降到 ~3ms**。
加上省掉的进程启动（~120ms），一扇新窗从 587ms 落到 200ms 量级——
与 WT 的 172ms 同档。剩下的主要是起 shell 的 196ms，那笔钱 WT 也付。

## 1. 现状事实（已核对代码，并在真机验证）

| 事实 | 依据 |
|---|---|
| 一扇窗 = 一个进程 = 一条实例记录 | `instances/alpha.json`、`bravo.json`，pid 各不相同 |
| 第二次启动会**领养**已有会话，而不是新开 shell | 真机：开 A、再开 B，两窗共 1 个会话 |
| `perform_close(EndSessions)` 销毁的是 `SessionEngine::list_sessions` —— Core 模式下那是**全局**列表 | `unterm-app/src/window.rs` |
| **关掉一扇窗会销毁另一扇窗的会话** | 真机：关 B 之后，A 仍活着但「无活动面板」 |
| 退出提醒有四种结果：后台继续 / 排空后退出 / 立即取消并退出 / 直接关闭 | `palette::Command` 四个分支 |
| 「后台继续」进托盘；没有托盘则降级为关闭 | `enter_background` |

最后一条现状是关键：**今天「窗口」「进程」「实例」是同一个东西**，
所以退出提醒只需要回答一个问题。单进程多窗口把这三者拆开之后，
同一个提醒要回答三个问题——这正是这件事的真正难点，也是它值不值得做的
分水岭。

顺带：第 3 行那条是**当前就存在的缺陷**，与本设计独立。今天开两扇窗就会
中招，见第 6 节。

## 2. 核心：退出到底在问什么

拆成三条互不相同的生命周期：

- **视图（窗口）**：看会话的一扇窗，可以有 N 个。
- **前端（进程）**：负责画、接键盘、托盘。
- **会话（Core）**：shell 与 agent 真正活着的地方，早已独立于前端。

今天的退出提醒把「关这扇窗」和「退出前端」合成一个动作，因为它们本来
就是一个。拆开之后需要五条决定：

### D1 关窗口只关视图，永不销毁会话

会话已经住在 Core 里，窗口只是投影。今天的 `EndSessions` 语义在 Core
模式下**已经是错的**（真机验证：它销毁别的窗口的会话）。

代价：与「关掉终端窗口 = 里面的程序结束」这个几十年的直觉相悖。
所以必须配 D2。

### D2 只有关掉**最后一扇**窗时才问退出提醒

只有这时才真的存在「会话何去何从」的问题。

- 还有别的窗开着 → 直接关，不问，不动任何会话。
- 这是最后一扇 → 问现在这三件事（后台继续 / 排空后退出 / 立即取消并退出）。

这条让 D1 不至于变成「会话静默泄漏」：用户仍然会在最后一刻被问到。

### D3 前端进程的存亡跟随窗口，按平台惯例

- Windows / Linux：最后一扇窗关掉 → 进程退出；除非用户选「后台继续」，
  那就进托盘（今天已有这条路）。
- macOS：应用惯例是没有窗口也留在 Dock 里，`Cmd+Q` 才退。

这条会让「退出」在两个平台上不是同一件事，必须在文案里说清，而不是靠
用户猜。

### D4 每扇窗记住自己的 pane，但所有权仍在 Core

`TabRegistry` 今天就是每窗一份，够用。它只用于 D2 的记账（这扇窗关掉后
还有没有别的窗在看这些 pane），不改变 Core 的所有权。

### D5 「新建窗口」应当新开 shell，不再领养

领养是为了「重开 GUI 后还能看到原来的 pane」，不是为了「我要一扇新窗」。
今天两者混在一起——真机验证：第二扇窗镜像了第一扇窗的 pane，用户想要的
显然不是这个。

单进程之后必须分清：
- 进程启动时的**第一扇**窗 → 领养 Core 中已有的会话（保住 M1 门禁）
- 用户主动**新建**的窗 → 新开 shell

## 3. 崩溃隔离：会失去什么

今天一扇窗崩溃只带走自己；单进程之后会带走所有窗口。

缓解的是 M1 已经建立的性质：**会话在 Core 里，前端崩溃不丢 shell 与
scrollback**（真机验证过）。所以代价从「工作没了」降级为「所有窗口要
重开一次」。

可选加固：把「重开后恢复所有窗口的布局」做成默认，而不是只恢复一扇窗。

## 5. 对外契约的影响

（以下为写作时的预判，实施后的实际结果附在每条后面。）

- `instance.list` 与 `--instance` 路由：今天一条记录一个 pid；之后会是
  **N 条记录共享一个 pid**，身份必须从 pid 换成 window id。
  → **没有这么做，而且不需要**。实例注册表仍是「一个前端一条记录」，
  窗口不各占一条；窗口身份走新的 `instance.windows`，`instance.list` 只在
  当前实例那条上挂一个 `windows` 数组。这样 pid 与记录仍是一对一，下面
  那条存活校验的问题就不存在了。
- 死记录清理：不能再用「pid 死了就清这条记录」——同一个 pid 下还有别的
  活窗口。刚修的 `client.rs` 存活校验需要同步调整。
  → **未发生**，见上：一个 pid 仍只对应一条记录。
- MCP `instance.focus`：语义仍然是「聚焦某扇窗」，不受影响。
  → **加了可选的 `window_id` 参数**。不带时仍是「前台那扇」，与旧调用
  完全兼容；指名一扇不存在的窗是报错，不是转投别的窗。

实施中额外发现、本节当时没有预料的两条：

- `session.focus` 只改全局 active session，而前端只在前台窗跟随。多窗口
  之后这等于「agent 说看这个、用户什么也没看见」。现在它会抬起持有该会话
  的那扇窗并返回 `window_id`。
- 会话归属。每扇窗都把 Core 的整份 session 列表镜像进自己的 tab bar，
  第二扇窗一出生就显示别的窗的 shell。规则收在 `window_should_adopt`：
  已在本窗的留着、别的窗持有的不抢、分屏跟着源 pane 走、剩下的孤儿由
  前台窗收下（这正好覆盖 MCP 建会话与 D1 关窗两种来源）。

## 6. 与本设计独立、但今天就在伤人的缺陷

`perform_close(EndSessions)` 用全局会话列表销毁 pane。今天开两扇窗，
关掉其中一扇就会销毁另一扇的 shell——真机验证：关 B 之后 A 仍在，但
「无活动面板」。

这条不需要等 A 落地，改成「只销毁这扇窗自己 `TabRegistry` 里的 pane」
即可，是个小切片。建议先修它。

→ **已先修**：`426e7f65`，正如建议的那样单独一刀，在 W-1 之前。

## 8. 落地与验收

**已验收（Windows 真机，装机版 0.68.3）**

| 规则 | 验收方式 |
|---|---|
| D1 关窗只关视图 | 关掉两 tab 的窗口 2，其 3 个会话全被窗口 1 接管，一个不丢 |
| D2 只在最后一扇窗问 | 关最后一扇窗弹确认、进程不退；`window_count_for` 成为唯一判据并被测试直接调用 |
| D5 新窗口不领养 | 两扇窗各自 1 个 tab，标题不再是 `[1/2]` |
| 会话归属 | 后台窗的分屏落在后台窗且是分屏不是新 tab；MCP 建的会话落焦点窗；销毁后台窗的 pane 后它立刻消失 |
| 窗口身份 | `instance.new_window` 返回 id、`instance.windows` 列出两扇、按 id 双向切换生效、不存在的 id 报错 |
| 跨窗 `session.focus` | 抬起持有该会话的窗，`focused` 随之翻转 |
| 开窗耗时 | 587ms → 31ms（W-3 提交内实测） |

**D3 的 macOS 分支（Mac 真机，2026-10-08，独立 state 目录的 master 构建）**

实测与 D3 原文不符：最后一扇**空闲**窗口关掉后整个应用退出、Core 一并停掉，
并不留在 Dock。`4946adab` 有意如此（`a_command_that_says_exit_always_exits`
断言 `WindowOnly + EndSessions` 退出）。**重新拍板：保持现状**——macOS 上
关最后一扇空闲窗口即退出。`last_window_close_ends_process()` 的「留进程」
分支在 macOS 上只剩一种入口：选了「后台继续」但菜单栏图标起不来。

| 场景 | 结果 |
|---|---|
| 最后一扇空闲窗口点关闭 | 进程退出，Core 停止（按新拍板） |
| 最后一扇窗有程序在跑点关闭 | 弹确认；选「后台继续」→ 窗口收起、Dock 图标隐藏、菜单栏图标出现，进程与 Core、程序都活着；菜单栏「打开窗口」→ 窗口回来、Dock 回来、原会话被领养 |
| 两扇窗关其中一扇 | 不问，只关视图，会话与程序都在（D1/D2 回归） |
| **Cmd+Q，有程序在跑** | **验收时发现缺陷**：不问就退出，Core 停掉，正在跑的程序被杀。已修：delegate 加 `applicationShouldTerminate:`，先取消、交给事件循环走与关窗相同的确认；不同于关窗，多扇窗时也问（退出会带走所有窗的会话） |
| Cmd+Q，两扇窗、有程序在跑 | 修后：前台窗弹确认；「后台继续」收起**两扇**窗；回来时一扇窗领养全部会话 |
| Cmd+Q → 立即取消并退出 | 进程退出、Core 停止 |
| Cmd+Q，只有一个空闲会话 | 直接退出，不问（与修前一致） |
| 注销 / 重启 / 关机 | 放行，不拦（Apple event 带 `why?` 原因时直接 `NSTerminateNow`） |

**崩溃隔离（Mac 真机，2026-10-08）**

临时构建在 `draw()` 开头注入 panic（未提交），两扇窗、三个会话各跑一个
`sleep`：

- panic 写入 `panic.log`，崩溃对话框弹出；点 Close 后进程退出，**两扇窗
  一起没**，没有冻住的残留窗口——与第 3 节预期一致
- Core 与三个会话（含两扇窗各自的 `sleep`）全部存活
- 重开后三个会话全部回来，但都在**一扇窗**里（三个 tab）；第 3 节的
  「恢复所有窗口布局」仍是可选加固，未做
